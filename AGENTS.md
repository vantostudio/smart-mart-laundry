## Architecture

- Next.js App Router, feature-sliced: routes in `src/app/(site)`, page code and static data in `src/features/<name>/` (`data.ts`, `components/`); the laundry basket and the shop bag live in `localStorage` via `src/features/cart/cart-provider.tsx`; checkout builds a WhatsApp deep link (`src/lib/whatsapp.ts`). Payment is on delivery (or in store) — no online payment UI.
- Hosting is moving to Cloudflare Workers via OpenNext (`@opennextjs/cloudflare`) in slice `hosting`; the repo has no Wrangler or OpenNext config yet. Server code targets the Node.js runtime with `nodejs_compat`. Never set `export const runtime = "edge"` (OpenNext doesn't support it) and add no `proxy.ts`: every admin page and action checks access itself. Why: [`docs/decisions/0001-neon-and-neon-auth-on-cloudflare.md`](docs/decisions/0001-neon-and-neon-auth-on-cloudflare.md).
- The backend is Neon Postgres plus Neon Auth (Google only), for the staff admin area (`/admin`) and the small public API the shop reads. Its server code lives in `src/lib/db` (Drizzle on Neon's HTTP driver, migrations in `drizzle/`) and `src/config/env.ts`. `src/features/admin/lib/auth.ts` holds the access check (`getAdmin`, `requireAdmin`, `requireAdminForAction`): every admin page must call `requireAdmin()` and every admin action `requireAdminForAction()`. Admin routes live in `src/app/(admin)` (its own bare layout, `noindex`); admin UI in `src/features/admin/components`, and every admin message in `src/features/admin/messages.ts`.
- Admin API routes live in `src/app/api/admin`; every handler is wrapped in `adminRoute` (`src/lib/api.ts`), which checks access, refuses cross-site writes and maps errors to statuses. Pass `{ role: "owner" }` to `adminRoute` for what only an owner may do. Products are in `src/features/products`: `condition` (new, mtumba) and `category` (ladies, men, shoes) are separate fields. Staff screens are `src/app/(admin)/admin/products`; they read with `listProducts`/`getProduct` and write through the API with `src/features/products/lib/api-client.ts`. Photos are in Neon Object Storage (bucket in `neon.ts`, `src/lib/storage.ts`, read with `storageEnv()`); `images` holds keys, never URLs. Every photo is uploaded with a ~480px thumbnail made in the browser (`shrink-image.ts`), stored at `thumbnailKey(key)` (`src/features/products/lib/image-keys.ts`); the shop's grids, rail and bag use it and fall back to the full photo. Deleting a product or dropping a photo removes both files after the database change, best effort (`src/features/products/lib/photos.ts`). Sizes come only from the lists in `src/features/products/sizes.ts`, and the API refuses anything else.
- Rate limits: `publicRoute` and `adminRoute` count every request through `src/lib/rate-limit.ts` (fixed window; the limits table sits at its top), so a route can't skip it. Public reads are keyed by client IP (`cf-connecting-ip`; `x-forwarded-for` and `x-real-ip` count only outside production, because a client can forge them); admin requests by IP first, then by signed-in person after the access check. Over the limit: 429, `RATE_LIMITED`, `Retry-After`, `no-store`, one warning log with route and group and never an IP. The store is in memory per Worker instance, a basic guard only; swap in a Cloudflare Rate Limiting binding with `setRateLimitStore` at deployment (`API_RATE_LIMIT`, see README). Never use the database as the store.
- Public pages stay static and client-loaded, with three exceptions that read the database on the server, only through cached functions tagged for invalidation (`src/lib/cache-tags.ts`): the site layout reads the shop settings with `getLiveShopSettings` (`src/features/settings/lib/live-settings.ts`, tag `settings`) and passes them to `ShopSettingsProvider` and the JSON-LD; `/shop/[code]` renders one product with `getCachedPublicProduct`, and `src/app/sitemap.ts` lists in-stock codes with `getCachedSitemapCodes` (both in `src/features/products/lib/cached-products.ts`, tag `products`). Nothing else in `src/app/(site)`, the public features or `src/components` may import server code or read the database; every other public read (the shop list, the quick view, the home rail) loads in the browser from `GET /api/products` and `/api/products/[code]`, wrapped in `publicRoute` (`src/lib/api.ts`), through `src/features/shop/lib/api-client.ts`. A cached read must use `use cache` with `cacheTag` and `cacheLife`, must never turn a database failure into a long-lived answer (settings fall back to the defaults for seconds; a product failure throws and is not cached, so it is never a cached "not found"), and its writer must call `revalidateTag(tag, { expire: 0 })`: every settings save and every product create, edit and delete does. `src/features/products/public.ts` holds what the shop may see: never `id`, `createdAt` or storage keys, and sold-out products don't exist publicly (`/shop/[code]` answers a real 404). Shop copy is in `src/features/shop/messages.ts`. Why and what Cloudflare needs: [`docs/decisions/0002-server-cached-public-reads.md`](docs/decisions/0002-server-cached-public-reads.md).
- Staff change delivery, phone and hours at `/admin/settings`, stored in the one-row `shop_settings` table, and that row is the only source: `src/config/shop-settings.ts` holds just the fallback defaults for when there is no database. Every page, the footer, the booking schedule and the JSON-LD (`businessJsonLd(settings)`) get the live values from the site layout; public components read them with `useShopSettings`, and server components use the pieces in `src/components/shared/contact.tsx`. There is no `/api/settings`.
- Never show or return an email: staff are told apart by name and role. `AdminContext.email` is for server code only, and `src/features/admin/lib/staff.ts` selects no email.
- Server modules import `server-only`. Their tests run in the default jsdom environment and start with `vi.mock("server-only", () => ({}))`, because `src/test/setup.ts` needs `window`.
- Env will come from Wrangler secrets and `.dev.vars` and be read lazily, so builds and checks run without secrets. The names are in `.env.example`. Never commit values.
- Orders, stock that goes down when something sells, tracking and M-Pesa still come later; keep the `features/*/data.ts` shapes easy to swap for API calls.
- Design system lives only in `src/app/globals.css` (primitives → semantic tokens → Tailwind theme); reference in `docs/design-system.md`. Clash Display headings and Satoshi content, self-hosted from Fontshare (ITF Free Font License, `src/app/fonts/`) with `next/font/local` in `src/app/layout.tsx`. Type and spacing step per device class (phone / tablet ≥640 / desktop ≥1024) — no `sm:`/`lg:` size overrides on headings. Never hardcode colors, sizes or fonts in components — use the semantic utilities (`bg-primary`, `text-clay-foreground`, `text-display-lg`, `container-page`, …).
- shadcn/ui: install only components that are actually used (`pnpm dlx shadcn@latest add <name>`); `src/components/ui` holds shadcn primitives restyled to our tokens; reusable site components live in `src/components/shared` (catalogue in `docs/design-system.md`).
- Tooling: pnpm + Vite+ (`vp test` / `vp lint` / `vp fmt` / `vp check`); Next.js owns `dev` and `build`. Unit tests sit next to the code (`*.test.ts(x)`); Playwright specs in `e2e/` run against a running server (`pnpm e2e`, see `README.md`).
- pnpm only: use `pnpm add`, `pnpm dlx` (for example `pnpm dlx neon@latest`) and `pnpm exec`, never `npm`, `npx` or `yarn`. When a tool's own instructions say `npm`/`npx`, translate them to pnpm.
